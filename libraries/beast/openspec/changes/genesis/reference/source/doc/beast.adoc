= beast: HTTP and WebSocket for WebAssembly
:toc: left
:toclevels: 2
:idprefix:
:sectanchors:
:attribute-missing: warn

`webcpp::beast` is a {cpp}20 compatibility facade for Boost.Beast applications.
It preserves Boost.Beast's messages, buffers and parsers while selecting a
transport appropriate to the program's environment. Native and WASIp3 socket
programs use the guest protocol engine. Browser clients use WebSocket and fetch;
WASI host HTTP programs use the host's request and response resources.
The application matrix distinguishes direct source compatibility from explicit
counterparts, since a browser client and a host HTTP handler do not own a TCP
listener.

[#beast-tutorial]
== Tutorial: construct a response

Use the library at `libs/beast` in the WebCPP superproject, with Boost 1.92 and B2
configured. This first example handles an in-memory request; it opens no connection.

[source,cpp]
----
include::{examples}/http_message.cpp[tag=handler,indent=0]
include::{examples}/http_message.cpp[tag=program,indent=0]
----

From the superproject root, run:

[source,bash]
----
unset CPATH CPLUS_INCLUDE_PATH C_INCLUDE_PATH
b2 -a libs/beast/example//http_message.output
----

The expected output is captured from the same example compiled against upstream Beast:

[listing]
----
include::{examples}/http_message.expected[]
----

The successful finish is a matched `.output` target. Compiling the executable alone
does not check its result.

[#beast-browser-tutorial]
=== Exchange a message in the browser

Configure Emscripten and the project's pinned Chrome. The browser driver serves
controlled local peers and the compiled page, runs JSPI and Asyncify, and checks
the page's result. It does not substitute Node for the browser.

[source,bash]
----
b2 -a toolset=emscripten variant=release libs/beast/example/browser//browser
----

The example resolves the local test peer and records its authority. These
operations then exchange a text message through the browser's WebSocket:

[source,cpp]
----
include::{examples}/browser/client.cpp[tag=browser-websocket-client,indent=0]
----

The synchronous interface suspends the {cpp} stack while the browser handles the
operation. Use the Asio suspension configuration supplied by the B2 dependency;
blocking the browser thread would prevent the event that completes the wait.

The same example sends an HTTP message through fetch and validates the response:

[source,cpp]
----
include::{examples}/browser/client.cpp[tag=browser-fetch-client,indent=0]
----

A successful page prints `browser tutorial: ok`; the driver requires that result
for both suspension variants. The controlled peer uses loopback HTTP. Production
HTTPS/WSS connections use the browser's certificate validation and trust store.

[#beast-host-tutorial]
=== Handle a host HTTP request

The WASI example receives an HTTP request from the host and returns a Beast
response. The host owns the listener, connection and any HTTPS termination:

[source,cpp]
----
include::{examples}/wasi/http_echo.cpp[]
----

[source,bash]
----
b2 -a toolset=clang-wasip2 variant=release libs/beast/example/wasi//http
b2 -a toolset=clang-wasip3 variant=release libs/beast/example/wasi//http
----

The served test checks the health response and echoed request body against the
example's recorded request transcript. A failed response, timeout or mismatch
fails the test. Supplying a guest TCP acceptor is unnecessary for this backend.

[#beast-how-to]
== How-to: select a dependency and target

[cols="1,2",options="header"]
|===
|B2 dependency |Purpose
|`/webcpp/beast//beast` |Portable buffers, HTTP messages, parsers and serializers.
|`/webcpp/beast//sockets` |Native/WASIp3 guest socket algorithms and Asio configuration.
|`/webcpp/beast//tls` |Guest-owned TLS with source-built OpenSSL.
|`/webcpp/beast//browser` |Browser-owned WebSocket, fetch and TLS policy.
|`/webcpp/beast//wasi-http` |WASIp2/P3 host HTTP resources, without guest sockets or OpenSSL.
|`/webcpp/beast//wasi-streams` |Explicit supplied-stream counterparts, including WASI CLI input/output.
|===

Include `<webcpp/beast/http/read.hpp>` and `<webcpp/beast/http/write.hpp>` explicitly
for byte-stream operations, and `<webcpp/beast/tcp_stream.hpp>` or
`<webcpp/beast/websocket.hpp>` for the socket types. The convenience header omits
these transport headers and `<webcpp/beast/ssl.hpp>`.

Select the dependency for the transport the application actually uses. A WASI
host HTTP handler does not need the guest socket or TLS dependency. Combining
backends is explicit, for example a WASIp3 service that accepts host HTTP requests
and separately contacts a TCP service.

[source,bash]
----
b2 -a variant=release exception-handling=on,off libs/beast/test libs/beast/example
b2 -a toolset=clang-wasip2 testing.launcher=wasmtime exception-handling=on,off libs/beast/test libs/beast/example
b2 -a toolset=clang-wasip3 testing.launcher=tools/boost/asio-wasip3/run.sh exception-handling=on,off libs/beast/test libs/beast/example
b2 -a toolset=emscripten exception-handling=on,off libs/beast/test libs/beast/example
----

WASIp3 socket tests require the launcher's loopback networking capabilities. Production
hosts should grant only the capabilities their application needs.

[#beast-configuration]
=== Configure error policy

`webcpp-beast-unsupported=error` is the default; `ignore` is the alternative intended
for documented host-adapter restrictions. It does not make an unavailable transport
work. The B2 feature defines exactly one of `WEBCPP_BEAST_UNSUPPORTED_ERROR` and
`WEBCPP_BEAST_UNSUPPORTED_IGNORE`. Defining both fails compilation.

`WEBCPP_BEAST_NO_EXCEPTIONS` follows `<webcpp/config.hpp>` and can also be defined by
the application. `WEBCPP_NO_EXCEPTIONS` applies to all WebCPP libraries. These macros
do not change the compiler configuration or remove upstream Boost overloads; use
`exception-handling=off` for a complete build without exception handling. Prefer
upstream error-code overloads when recovery is required.

[#beast-explanation]
== Explanation: separate messages from transport

Boost.Beast's general headers include stream algorithms that reach Asio sockets.
A message-only application does not need those dependencies, even though the
Asio port now offers a WASIp2 socket reactor. This facade exposes data headers separately,
retaining upstream type identity and parsing behaviour without a guest reactor.

The socket backend executes upstream Beast over the existing Asio port. Host
adapters map operations to browser WebSocket/fetch and `wasi:http`, preserving
application-visible messages with documented differences in connection ownership,
headers, framing and TLS. A host HTTP handler does not imply a TCP acceptor.

For a server counterpart, keep the application's HTTP request processing and
replace its accept loop with the host handler entry. For a local-stream
counterpart, explicitly supply the two stream directions; stdin and stdout do
not provide Unix socket names, descriptor passing or peer credentials.

Browser security remains the browser's: CORS, forbidden request headers,
certificate validation, redirects and WebSocket control frames cannot be
implemented as arbitrary raw-socket options. Host TLS never uses guest OpenSSL
settings. Prefer explicit errors to silently claiming that the host accepted an
unavailable setting.

The native/WASI WebSocket allocator constructor accepts the portable constructor
syntax, but upstream Beast still controls its internal stream-state allocation.
Associated completion-handler allocators retain upstream semantics. Data containers
use their upstream allocator template parameters.

`set_server_name` configures SNI only. It copies a non-terminated string view into a
bounded buffer and rejects empty, overlong or embedded-NUL hostnames. Certificate and
hostname verification remain separate TLS settings. Guest OpenSSL settings must never
be represented as changing browser or WASI host trust policy.

[#beast-matrix]
== Feature matrix

Capabilities belong to a backend, not only a compiler target. The runtime record
below and the application matrix state which variants were actually exercised.
An application counterpart preserves a stated use case; it does not imply every
API or transport detail of the original program is available.

[cols="2,1,1,1,1",options="header"]
|===
|Feature |Native |WASIp2 |WASIp3 |Emscripten
|HTTP message/parser/serializer interfaces |Implemented |Implemented |Implemented |Implemented
|Guest HTTP/WebSocket socket engine |Asio sockets |Asio core available; guest-socket facade/application integration pending |Asio socket port |Explicit supplied byte stream only
|Browser WebSocket and fetch |Not applicable |Not applicable |Not applicable |JSPI and Asyncify
|Guest TLS, identity verification and shutdown |Source-built OpenSSL |No guest TLS backend |Source-built OpenSSL |Browser owns TLS
|Host HTTP entry/client |Not applicable |wasi:http |wasi:http |fetch client only
|Unix socket namespace and peer identity |Operating-system sockets |Unavailable |Unavailable |Unavailable
|Explicit supplied-stream counterpart |Borrowed descriptors |CLI input/output; asynchronous WebSocket via pollables |CLI input/output |Caller-supplied channel
|Raw TCP HTTP/WebSocket listener |Available |Use host HTTP entry |Available |Unavailable
|Host HTTP WebSocket upgrade |Not applicable |Not provided by host adapter |Use guest socket backend |Browser WebSocket client only
|Native CPU-parallel threads |Available |Unavailable |Cooperative WASI threads only |Not implied by this backend
|===

Exception and thread variants are reported separately in the verification record.
Emscripten data tests run under Node; transport tests run in the pinned Chrome.
Cooperative WASIp3 threads are not CPU-parallel threads, and their SDK 34 runtime
currently requires exceptions off.

[#beast-stream-cancellation]
=== Cancellation of host-supplied streams

The WASIp2 WebSocket counterparts use Asio's pollable-driven CLI adapter and
retain asynchronous read/write operations. Their actual client/server exchanges
pass with both exception profiles. The P2 Asio supplied-stream lane checks a
pending read with open, empty input, timer cancellation, cancellation slots,
stream destruction, deferred initiation and handler allocator/executor associations.
Other supplied counterparts retain their explicit synchronous partial operations.

Supplied-stream cancellation is checked between host calls and while waiting on
supported readiness operations. It cannot preempt a host import that blocks the
calling thread. In the tested Wasmtime 50 CLI, WASIp2 stdout can block when its
operating-system pipe fills even after `check-write` grants permission. A paused
consumer must resume draining before that import returns and the component can
observe cancellation. Keep the consumer draining or select a host/channel with
nonblocking write behaviour when a strict cancellation deadline is required.

This is separate from a guest socket's cancellation semantics. Standard input
and output also do not acquire Unix socket addressing or peer credentials merely
because they are exposed through file descriptors.

[#beast-guarantees]
== Guarantees and evidence

* `message_test.cpp` checks upstream type identity, embedded-NUL payloads, parser body
  limits and malformed fields on every declared data target.
* `socket_test.cpp` exchanges real HTTP and binary WebSocket payloads, completes both
  sides of a close handshake, and verifies a stalled peer reaches the stream timeout.
  Each case has a five-second outer deadline.
* `ssl_test.cpp` checks SNI copying and rejection without replacing an existing valid
  name. It does not claim that an SNI setting authenticates the peer.
* `config_test.cpp` checks compiler/global/library exception configuration, both
  unsupported-operation policies and rejection of conflicting definitions.
* `test/tls/protocol.cpp` checks actual TLS HTTP and WebSocket exchanges,
  authentication failures, transfer cancellation and TLS shutdown outcomes.
* `test/browser/browser_test.cpp` runs the browser contracts in Chrome. Its local
  server controls delayed headers and bodies, redirects, WebSocket closure and CORS.
* `test/applications/inventory.py` verifies all 53 pinned upstream executables and
  their source hashes; application drivers compare explicit local exchanges.
