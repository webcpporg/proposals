[#beast-browser-differences]
=== Browser settings and observable differences

This table describes the browser-owned WebSocket and fetch backends. It does not
change native or WASIp3 guest socket semantics. `ERROR` rejects an unsupported
setting with `operation_not_supported` when the dependent operation starts.
`IGNORE` discards that setting; it does not add a missing browser capability or
disable browser security. Configuration is part of the browser types' namespace;
translation units using different policies cannot exchange those types silently.

The browser-owned WebSocket's `websocket::request_type` uses
`http::basic_fields<std::pmr::polymorphic_allocator<char>>`. Its handshake fields
therefore use the stream's memory resource, including long decorator values.
Use that alias, or a generic callable, when declaring a request decorator rather
than requiring Boost's default field allocator. Native and WASIp3 socket streams
retain the upstream request type. The explicit guest WebSocket adapter accepts
typed WebCPP request and response decorators for client and server handshakes;
it converts their fields when calling the upstream protocol implementation.

The test harness configures an ephemeral CA in a disposable full-Chrome profile.
The protocol contract peer's certificate covers `localhost` and `127.0.0.1`;
an untrusted profile rejects its WSS connection before the trusted contracts run.
Application HTTPS fixtures use a separate localhost-only certificate to prove
that a trusted certificate is still rejected for the wrong hostname. These
fixture settings belong to the host harness and do not add guest TLS controls.

A successful WebSocket write means the browser accepted the message, not that the
peer received it. Partial writes are accumulated into one message, and their
bytes count toward the send bound. A cancelled read leaves the next message
available to a later read. Destruction aborts pending operations through posted
completion and unregisters event callbacks before late events can reach them.
Both queue bounds default to 4 MiB. The default maximum WebSocket message is
16 MiB; a smaller receive-queue bound still applies independently.
The receive bound charges each retained payload and its message record, including
empty messages. Partial reads release that charge only when the complete message
is consumed and its storage is released. Container bookkeeping and allocator
overhead are additional implementation costs; the bound is not a total heap quota.

The default HTTP path maps messages directly to fetch. Its response body limit
defaults to 8 MiB. `http::async_read_header` and `http::read_header` accept response
messages and complete when metadata is available, before the body is consumed;
a subsequent full read consumes the body. The separate
`http_byte_stream` compatibility adapter synthesizes HTTP/1.1 bytes for programs
using Beast parsers, buffering the full fetch response before parsing. Fetch has
already decoded the response body, so synthetic
responses omit original `Content-Encoding` and `Content-Length`; responses with
a body use chunked framing. HEAD, 204 and 304 responses have no synthetic body
or chunk terminator. HEAD parser users retain `skip(true)`. These representation
differences do not imply byte-for-byte equality with the original wire response.
