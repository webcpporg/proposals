[#asio-feature-matrix]
=== Feature matrix by library and build profile

This records the WebCPP integration and capability-completion work verified
on 2026-11-03, using
Boost 1.92.0, Emscripten 6.0.11 and wasi-sdk 34.0. The project now selects
Wasmtime 50.0.1 for its regression suites; the original isolated probes used
Wasmtime 49.0.3. It is not a
list of everything those upstream projects might support in other builds.
The Asio target is `/webcpp/asio//asio`; the Cobalt integration is
`/webcpp/asio//cobalt`, using Boost.Cobalt's names. Do not infer that an Asio
feature has also been tested through a Cobalt wrapper or completion token.

Each cell describes the named feature, not every overload or possible input.
Read the profile availability table first: an unavailable profile makes all
of its public features unavailable, even if an isolated source file compiles.

.Status legend
[cols="1,5",options="header"]
|===
| Mark | Meaning
| T | Tested: the named behavior has local runtime evidence in this profile.
| A | Provided by the backend or Boost contract; dedicated runtime validation
is pending. Treat this as a validation task, not as a tested support guarantee.
| L | Limited: usable only within the restriction explained beside the table.
| U | Unverified: there is insufficient evidence to promise this combination.
| X | Unavailable through this integration or the tested toolchain.
| B | Build integration blocked: WebCPP rejects the library target before
compilation. Read the named blocker; this does not establish a platform limit.
| P | Probe only: isolated runtime evidence, outside the public library target.
This is progress toward a port, not an available application configuration.
| C | Compile only: an isolated source compiles; linking and execution are unverified.
| N/A | The feature is specific to another environment.
|===

*Native S is not a promise of no threads.* The native build does not set
`BOOST_ASIO_DISABLE_THREADS`. Boost may use internal threads, for example for
asynchronous name resolution. Explicitly disabling Asio threads is a different
configuration and must be applied consistently to the application and compiled
dependencies. It does not disable unrelated libraries' threads.

Browser S sets `BOOST_ASIO_DISABLE_THREADS`; explicit M enables pthreads in
the application and compiled dependencies. WASIp3 S also disables Asio threads. WASIp3 M
uses cooperative threads, not simultaneous CPU execution on multiple cores.
The missing cooperative EH runtime is a limitation of the SDK distribution
tested here, not proof that threads and exceptions are fundamentally incompatible.

`variant=release/debug` changes optimization, not these feature declarations.
The WASIp3 evidence here uses Release. Native operating-system features remain
subject to Boost and the host OS; macOS results are not Windows or Linux tests.

Both profiles use native asynchronous forward lookup with a waitable-backed

[#asio-feature-cobalt-build-block]
===== How the Cobalt source integration works

The target builds the normal compiled archive, replacing its endpoint and
acceptor source files with checked private copies. The private header overlay
uses Asio capability macros to omit unsupported local-socket, signal and serial
APIs. Seqpacket declarations are omitted when that socket type is unavailable.
Single-thread builds omit the thread source and declaration; cooperative builds
include it. Native and browser builds retain their original sources and headers.

The application, archive and replacement runner use the same patched Asio
headers, thread profile and exception setting. No system Cobalt archive is
linked, and installed Boost files are never modified. Input/output hashes pin
the compatibility patch to Boost 1.92. A changed upstream input is rejected.

The public-target tests cover both Cobalt completion tokens applied to Asio
sockets and Cobalt's own compiled TCP/UDP wrappers, with IPv4 loopback traffic,
refused TCP connections, TCP EOF and TCP/UDP cancellation.
TLS tests add the ordinary Asio/OpenSSL stream and
Cobalt token, with custom or embedded CAs and peer identity verification.

SDK 34.0 maps nonzero command returns to failure: the host statuses are 0 for
`co_return 0` and 1 for `co_return 7`. The status driver checks both output and
status, so a trap cannot satisfy the failure case. No host shutdown protocol
has been added. See <<asio-cobalt-runner>> and <<asio-cobalt-status>>.

[#asio-feature-errors]
==== Exceptions and error handling

[cols="3,3,3",options="header"]
|===
| Behavior | EH on | EH off
| Error-code overloads and callback error parameters
| Available where the underlying operation is available
| Same error channels; no exception is needed to report an ordinary I/O error
| Result/tuple adapters around an asynchronous wait
| Available | Available for the tested paths; underlying operation support still applies
| Throwing overload invoked on an error
| Can report an exception according to the API contract
| May be excluded by the wrapper or reach the fatal Boost exception handler;
do not treat it as an error-code overload
| Exceptions escaping a coroutine
| Follows the coroutine's documented propagation policy
| No guarantee of recoverable propagation; use supported result-based paths
| Cobalt pending-task move with `libc++`
| No exception-disabled limitation claimed here
| Known abort risk linked to https://github.com/boostorg/cobalt/issues/287[Cobalt issue 287]
| WASIp3 cooperative profile in SDK 34.0
| Missing runtime in this distribution | Available for the tested Asio feature set
|===

Result adapters do not repair a library operation that constructs an exception
object internally. The Cobalt EH-off build warning is a configuration warning,
so the compiler's warnings-as-errors setting does not turn that warning into
a build failure. It remains a restriction the application must account for.

[#asio-feature-restrictions]
==== Restrictions, causes and application consequences

[cols="2,3,4",options="header"]
|===
| Restriction | Cause | Consequence or required work
| WASIp3 cooperative threads with EH
| SDK 34.0's cooperative sysroot is built without the {cpp} exception runtime
| Use S/EH on or M/EH off. Supporting M/EH on needs a matching runtime build
and runtime validation, not just adding `-fexceptions` to an application.
| Native S versus disabled thread support
| `threading=single` does not define `BOOST_ASIO_DISABLE_THREADS` natively
| Native S can still use internal threads. Explicit thread disabling needs
consistent library/application settings and its own validation.
| Browser M hosting and affinity
| Pthreads need isolated shared memory; JavaScript values have thread affinity
| Use the creator thread to run each context and the main executor for DOM work.
Configure COOP/COEP when hosting; compiler macros cannot verify deployment.
| Browser sockets and TLS
| The default transport returns `operation_not_supported`; only a transport
interface and TLS settings are supplied
| Supply and validate an adapter. These APIs do not expose raw browser TCP/UDP
or provide an OpenSSL stream. See <<asio-sockets>>.
| WASI reverse DNS and canonical/mapped-name policies
| The host lookup interface supplies forward address results
| Unsupported async policies report `operation_not_supported`. Host DNS permission
remains a runtime fact; numeric and forward lookup paths are available.
| WASIp3 UDP buffer sequences
| The tested wasi-libc lacks the vectored socket calls used by stock Asio
| The port supplies gather sends and scatter receives, including connected sends,
with temporary allocator-aware storage. See <<asio-wasip3-contract>>.
| WASIp3 socket options and IPv6 scopes
| The port exposes only the tested libc interfaces
| Missing options return `operation_not_supported`; interface-name scopes are
rejected. Numeric IPv6 scope parsing is tested, IPv6 traffic is not.
| WASIp3 process signals and OS-specific devices
| This port has no POSIX signal service, local-socket family or serial backend
| There is no automatic SIGINT/SIGTERM cancellation. Explicit operation
cancellation works; a host shutdown protocol would be separate integration work.
| Cobalt pending-task move without EH
| Boost 1.92's move path can construct an exception with `std::make_exception_ptr`;
the reported `libc++` no-EH configuration aborts
| See https://github.com/boostorg/cobalt/issues/287[issue 287]. This concerns
the pending task's move implementation, not every `std::move` or every coroutine.
Result adapters do not repair this internal path. Other coroutine families
still need their own success, error and cancellation tests.
| Cobalt `io::ssl::stream`
| Available through an optional target with a checked Boost 1.92 patch
| `/webcpp/asio//cobalt_ssl` adds the wrapper, state/callback corrections and
`native_ssl_handle()` extension. Native, P2 S and supported P3 profiles are
available; browser TLS remains host-owned. See
<<asio-cobalt-ssl>> for trust configuration and the STARTTLS contract.
|===

[#asio-feature-validation-pending]
==== Validation still required

A and U are open validation work, not reasons to skip testing. C needs linking
and runtime checks. P needs the same behavior tested through the public target.
This inventory groups the remaining gaps; each test must record its target,
thread/EH profile, tool versions and observed success or supported failure.

[cols="3,5",options="header"]
|===

The commands in <<asio-wasip3>> and <<asio-cobalt-verify>> reproduce the
registered lanes. To promote U, C or P to T, record a successful runtime test
through the intended public target, including the relevant thread and EH
profile. Keep unsupported-operation tests as evidence of a limit, not evidence
that the rejected operation is supported. Update this matrix when a backend,
toolchain, capability guard or test result changes.
