[#asio-testing]
== Testing

[#asio-testing-application]
=== How to test your application

For a small program with deterministic text output, follow the compiled
examples: keep an `.expected` file beside its source and declare the program
with `webcpp.example` in its example Jamfile. Run the native target first,
then Emscripten with JSPI and Asyncify. Compare observable completions and
error values; avoid exact elapsed-time assertions, since the host can
resume a ready operation later than its deadline.

Keep the context and objects captured by handlers alive until their work
finishes. A cancelled operation must still complete with its cancellation
error; merely requesting cancellation does not prove that it was delivered.
Use <<asio-quick-start>> and <<asio-timers-example>> as executable starting
points. Native and Node runs do not establish browser rendering behaviour;
use a real browser when your contract depends on page events or animation.

[#asio-testing-library]
=== What the library checks

asio's tests are under `test/`, each declared in `test/Jamfile` with
webcpp's rules, for two targets, native and emscripten:
{n-tests} tests in all, {n-tests-native} natively and {n-tests-emscripten}
on emscripten, run by node. Each public header is also compiled alone, as
the only include of its translation unit, so that a header that leans on an
include it does not make fails, naming it.

`<webcpp/asio/config.hpp>`, which every public header of asio includes
first, defines `WEBCPP_ASIO_NO_EXCEPTIONS` when the build has no exceptions,
and a program may define it itself to turn asio's exceptions off in a build
that has them, as Boost.Asio's `BOOST_ASIO_NO_EXCEPTIONS` does. The tests
`config` and `config_developer_defined` check both ways it is defined.

[#asio-testing-lanes]
=== The lanes

The continuous integration runs asio in four lanes, each built from scratch
with `b2 -a` and a `--build-dir` of its own. From the root of a webcpp
checkout:

native::
Every test and example, natively:
+
[source,bash]
----
b2 libs/asio/test libs/asio/example
----

emscripten::
The same on emscripten, in the default suspension variant, JSPI, each
program run by node:
+
[source,bash]
----
b2 toolset=emscripten libs/asio/test libs/asio/example
----

asyncify::
A lane of asio's own, on emscripten: every browser test again under
Asyncify, the other suspension variant, and the size table of both. To
execute the guide examples under Asyncify too, run the second command:
+
[source,bash]
----
b2 toolset=emscripten libs/asio/test//asyncify libs/asio/example//asyncify
b2 toolset=emscripten webcpp-suspend=asyncify libs/asio/example
----

browser::
A lane of asio's own, on emscripten: the loader that picks a variant, under
node, and in headless Chrome a page program that never polls, a page that
keeps rendering, and the variant the loader picks:
+
[source,bash]
----
b2 toolset=emscripten libs/asio/test/browser//browser
----

`b2 libs/asio/test//config` builds and runs one test alone, while working on
it.

[#asio-testing-browser]
=== Browser observations

`browser_idle`, `browser_render` and `browser_loader` run real page programs
in headless Chrome, on both JSPI and Asyncify. The driver serves only its
page, loader and build artifacts on loopback HTTP. Set `CHROME` to the
browser executable; on macOS it otherwise finds the newest installed
Playwright headless shell. Each driver has a 120-second outer bound and
removes its Chrome process and temporary profile on success, failure or a
termination signal.

An idle context with outstanding work must schedule exactly one positive
`setTimeout`, at most 300 seconds, during a three-second observation.
Calls to `setInterval` and `MessagePort.postMessage` are recorded too, so
repeated polling cannot pass as a wait.

A self-posting handler runs for one second. The bounded run must allow at
least ten animation callbacks; Boost's unbounded control must allow none
between the program's start and completion. Callback entry times use
`performance.now()`, not the frame timestamp supplied by
`requestAnimationFrame`. This observes animation opportunities, not
individual painted pixels or a universal frame-rate guarantee.

The yield's `MessageChannel` records each complete turn of 1,000 handlers,
from resumption to the next post. The first starts at the program's
`spinning` line; the final partial turn is not a full-lot sample. Three
runs record callback and handler counts, turn counts, p95 and maximum
turn duration in the library's `AGENTS.md`. A p95 above 8 ms in either
variant stops the task for the owner to decide the default. A run with
no animation callbacks also stops for a decision about the witness.
The maximum is reported separately. Heavy individual handlers can still
block the page regardless of the handler-count limit.

The loader check runs the three-handler page normally and again after
removing `WebAssembly.Suspending` before navigation. The page identifies
the actual imported URL against the manifest before awaiting its factory,
so a JSPI program whose `main` never returns can still report its variant.
Any page exception, `console.error` or recorded loader error fails the run.

[#asio-testing-report]
=== The test matrix

Each lane records what b2 built and ran, and webcpp's
`tools/report/report.py` merges the records of every lane into a matrix: a
page of the libraries by lanes, and a page of each library's tests and
examples by lanes, where each cell says whether that program passed in that
lane, or how it failed, at compile time, at link time or when it ran. The
matrix is published with the documentation, at
https://webcpporg.github.io/webcpp/report/.

[#asio-testing-sizes]
=== How to compare the WebAssembly sizes

Build the page-ready variants of all three examples and their table:

[source,bash]
----
b2 toolset=emscripten libs/asio/example//asyncify
----

The build prints three rows and writes `asio.sizes.md` under its example
output directory. Each row contains the `.wasm` byte count for JSPI and
Asyncify and their ratio. These are page modules, built without the Node
test harness. The table excludes JavaScript glue, transfer compression and
runtime memory. Compare matching compiler settings and build variants;
debug artifact sizes do not predict release download sizes.
