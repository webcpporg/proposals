[#asio-capabilities]
== Target and variant capabilities

This reference covers the public feature families of `webcpp::asio` and its
Cobalt build target. It does not promise every feature of the complete Boost
installation. *Supported* means the implementation provides the feature;
*limited* requires the qualification below; *unverified* is not a portability
promise. Native behavior also depends on the operating system.

For the explicit feature-by-feature intersection of threads and exception
handling, use <<asio-feature-matrix>>. It separates Asio from Cobalt and
distinguishes public support, isolated probes and unverified combinations.

[#asio-capabilities-config]
=== Build configurations

[cols="2,2,2,3",options="header"]
|===
| Target and variant | Threads | Exceptions | Status
| Native | OS threads, subject to Boost configuration | On or off
| Existing integration; native controls run on macOS arm64.
| Emscripten / JSPI | Disabled in this integration | On or off
| Existing browser integration; Wasm exceptions when enabled.
| Emscripten / Asyncify | Disabled in this integration | On or off
| Existing browser integration; JavaScript exceptions when enabled.
| WASIp3 / `threading=single` | Disabled | On or off
| Minimal port; both configurations tested with wasi-sdk 34.0 and Wasmtime 50.0.1.
| WASIp3 / `threading=multi` | Experimental cooperative threads | Off
| Minimal port; tested with wasi-sdk 34.0's cooperative sysroot and Wasmtime 50.0.1.
| WASIp3 / `threading=multi` | Experimental cooperative threads | On
| Unavailable with the tested SDK: its cooperative sysroot has no {cpp} exception runtime.
| WASIp2 / `threading=single` | Disabled | On or off
| Core, timers, TCP/UDP, forward DNS and CLI streams tested; see <<asio-wasip2>>.
| WASIp2 / `threading=multi` | Unavailable | On or off
| Rejected by the build; no cross-thread reactor wakeup is provided.
|===

`variant=debug` and `variant=release` select build optimization, not different
APIs. The new WASIp3 runtime verification uses Release builds. JSPI and Asyncify
are browser suspension variants; they are not WASIp3 variants. The WASIp3
thread setting and exception setting are independent choices, subject to the
SDK runtime availability above. Cooperative threads suspend at blocking WASI
operations; this does not provide simultaneous CPU execution on multiple cores.

WASIp3 keeps Boost.Asio's scheduler and select reactor. It does not use the
JavaScript event bridge or the browser's handler-count limit. Its syscalls
suspend through wasi-libc and the host's Component Model implementation.

The public Cobalt target builds its static archive with checked compatibility
headers and sources on WASIp3. Timers, TCP/UDP and cancellation are exercised
through both Asio completion tokens and Cobalt's own wrappers. The optional
`/webcpp/asio//cobalt_ssl` target adds Cobalt's SSL wrapper with verified TLS
and handshake/transfer cancellation, including partial composed operations.
Truncated and cancelled shutdown are also tested; see <<asio-cobalt-ssl>>. See
<<asio-feature-cobalt-build-block>> for integration details and
<<asio-feature-validation-pending>> for open tests.
It has no automatic SIGINT/SIGTERM shutdown bridge on WASIp3; internal
coroutine cancellation is a separate mechanism. See <<asio-cobalt-runner>>.

OpenSSL local coverage includes native macOS arm64 single/multi with exceptions
on/off using Clang, WASIp3 single with exceptions on/off, and WASIp3 cooperative
with exceptions off. A GCC 15 native multi-threaded build with exceptions also
passed the TLS tests. Linux Clang/GCC mappings are implemented but not runtime-tested
on this macOS host. The native MSVC recipe is unavailable. The source library
uses OS threads natively and cooperative threads on WASIp3; it does not make
cooperative execution CPU-parallel. TLS tests cover verified handshakes,
asynchronous application data, clean shutdown and rejected peer identities.
The embedded CA factory's trust policy, update procedure and local checks are
documented in <<asio-ca-certificates>>.

The browser's default socket transport reports `operation_not_supported` for
network operations. The browser resolver does not perform DNS; see
<<asio-sockets>>. A TLS settings record is not a TLS implementation.

[#asio-wasip3-contract]
=== WASIp3 limits and error behavior

* TCP buffer sequences advance one nonempty buffer per syscall when necessary.
  Partial reads and writes are valid Asio behavior; composed `async_read` and
  `async_write` continue until their completion condition is met. No temporary
  heap buffer is introduced to concatenate a sequence.
* UDP `send_to` and `async_send_to` concatenate multiple nonempty buffers into
  one datagram because the tested wasi-libc does not provide `sendmsg`.
  Concatenation visits the entire sequence before Asio's native iovec limit.
  It copies the payload once into temporary storage: the context allocator
  supplies synchronous storage, and the handler's associated allocator supplies
  asynchronous storage. The operation owns asynchronous storage until completion
  or destruction and releases it before invoking the handler. Scalar, empty and
  single-nonempty-buffer sends need no temporary allocation or payload copy.
  The gather path rejects payloads above 65,535 bytes with `message_size` before
  allocating or reading their data; the host may enforce a smaller IP limit.
  Allocation failure follows the supplied allocator's failure behavior.
* UDP receive and connected `send` / `async_send` still accept at most one
  nonempty buffer. More are rejected before consuming or sending a datagram.
  Empty buffers do not split a datagram. Empty datagrams are delivered.
* Synchronous resolution uses wasi-libc. Actual hostname lookup requires host
  permission; numeric resolution does not need DNS. The single-thread profile
  cannot run Boost's resolver thread pool, so async initiation posts the
  unsupported-operation result to the executor. It does not start a hidden thread
  or throw during initiation for this condition.
* Interface-name scopes such as `%eth0` are rejected. Decimal IPv6 scopes in
  the range 0 through 4294967295 are accepted.
* Missing socket options, including linger, broadcast, debug, don't-route,
  out-of-band-inline and low-water marks, report `operation_not_supported`.
  Other options remain subject to wasi-libc and host support. Multicast and
  detailed socket-option interoperability have not been validated.
* WASI has no `ESHUTDOWN`. The port maps Asio's `shut_down` to `EPIPE`, which
  wasi-libc uses; it therefore shares the numeric value of `broken_pipe`.
* Error-code overloads and asynchronous completion retain their error channels.
  With exceptions disabled, invoking a throwing overload on an error can still
  reach Boost's fatal exception handler. Prefer explicit error-code/result paths.
* Cobalt uses the same platform restrictions through its public B2 target.
  Its async resolver reports `operation_not_supported` without threads; the
  cooperative profile uses the resolver worker pool. TLS through Asio/OpenSSL
  with Cobalt tokens uses application-selected trust roots and host network
  capabilities; embedded roots require no certificate filesystem preopen.
  See <<asio-tls>> and <<asio-ca-certificates>>.

These are current port boundaries, not claims that WASIp3 itself can never
support the missing operations. The compatibility patch belongs to Boost.Asio's
platform layer; implementing the missing POSIX entry points such as
`sendmsg`/`recvmsg` belongs in wasi-libc. The current port avoids pretending those
entry points or process signals exist.
