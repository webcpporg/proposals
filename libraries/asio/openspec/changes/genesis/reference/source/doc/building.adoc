[#asio-building]
== Building

asio is developed inside the webcpp superproject, as a Boost library is
developed inside Boost. Its headers share Boost's executor model; the browser
bridge and optional Cobalt entry point have compiled support units. A b2
program uses `/webcpp/asio//asio` on native, Emscripten and WASIp3:

[listing]
----
exe app : app.cpp /webcpp/asio//asio ;
----

The target adds asio's headers, Boost's and the webcpp configuration dependency.
`<webcpp/asio/config.hpp>` includes `<webcpp/config.hpp>` first;
`WEBCPP_NO_EXCEPTIONS` disables asio's throwing APIs even when the compiler
supports exceptions. An explicit `WEBCPP_ASIO_NO_EXCEPTIONS` remains supported.
On emscripten the target also supplies everything
else a program needs there: the define Asio needs to build, embind, the
JavaScript functions asio calls, compiled once in `src/browser_src.cpp`,
the link flags of the program's suspension variant, and the variant in the
program's name:

[listing]
----
include::{library-root}/build.jam[tag=asio]
----

Asio needs `BOOST_ASIO_DISABLE_THREADS` on emscripten: without it, Asio
decides it has threads under any compiler that defines `+__GNUC__+` outside
Linux, Emscripten's among them, and `<boost/asio/io_context.hpp>` stops at
"Only Windows and POSIX are supported!". The page has no threads, and the
target defines it for every program that uses it on emscripten. Asio's
inline namespace differs with and without threads, so a translation unit
that missed the define fails at link, never silently.

The bridge's JavaScript uses `stackSave` and `stackRestore`. On Emscripten
6.0.11, their native dependencies must survive the native link before
`EM_JS_DEPS` is processed. The target therefore exports
`emscripten_stack_get_current` and `_emscripten_stack_restore` explicitly,
including in optimized JSPI builds. A build outside b2 must keep the same
link flags shown above.

[#asio-building-variants]
=== The two suspension variants

On emscripten, `run` suspends `main` into the browser's event loop in one of
two ways, each a variant of the program built from the same sources:

[cols="2,5,2,3,2",options="header"]
|===
| Variant | What suspends | Link flags | Exceptions | Browsers

| `jspi`, the default
| JavaScript Promise Integration: the suspending imports, Emscripten's
  `+__syscall_poll+` and asio's yield, are wrapped in
  `WebAssembly.Suspending`, and `main`, on whose stack `run` executes, in
  `WebAssembly.promising`.
| `-sJSPI`
| WebAssembly exceptions, `-fwasm-exceptions`
| those with JSPI

| `asyncify`
| Emscripten's Asyncify: the compiler instruments every function that may
  reach a suspending import, so that the stack unwinds into the browser and
  is rewound when the program resumes.
| `-sASYNCIFY`, `-sASYNCIFY_STACK_SIZE`, measured
| JavaScript-based exceptions, `-fexceptions`
| every browser
|===

A build asks for a variant with the feature `webcpp-suspend`, on b2's
command line, `b2 toolset=emscripten webcpp-suspend=asyncify`, or in a
program's requirements, `<webcpp-suspend>asyncify`. The feature is
propagated, so that every library a program uses is built for its variant,
and composite, since Asyncify does not work with WebAssembly exceptions:
emcc only warns, and the program traps at run time with
`RuntimeError: unreachable` when it suspends inside a `catch` block. So
`asyncify` asks for JavaScript-based exceptions itself, and `jspi` keeps
b2's WebAssembly ones; a build with `exception-handling=off` compiles with
`-fno-exceptions` in either:

[listing]
----
include::{webcpp-root}/tools/webcpp.jam[tag=suspend]
----

Emscripten finds the suspending imports itself, so no list of them is
given. `ASYNCIFY_IGNORE_INDIRECT` is not set, since the path from `main` to
the reactor's `select` passes a virtual call, Asio's
`scheduler_task::run`. Asyncify adds instrumentation and increases the
program size. With `-O3` and exceptions enabled, the release examples
measured 1.88 to 1.91 times the JSPI WebAssembly size. The ratio depends on
the optimization profile and exception setting; see <<asio-testing-sizes>>
for the six-profile matrix with exceptions on and off, separate JavaScript
byte counts, build and execution timings, and reproduction commands.

[#asio-building-asyncify-stack]
==== Asyncify's stack

Asyncify saves a suspension in a stack of its own, of a fixed size, which
`ASYNCIFY_STACK_SIZE` sets and Emscripten allocates at every suspension:
each frame from `main` down to the suspending import writes its locals
there as it unwinds, and a suspension that does not fit traps with
`RuntimeError: unreachable`, which Emscripten follows, in a build with
assertions, with "may be due to ASYNCIFY_STACK_SIZE not being large
enough". The trap is certain, at every suspension that deep, but only
there. So asio does not keep Emscripten's default: it sets the size to at
least twice the deepest suspension its tests reach, measured exactly, as
the bytes each unwind wrote, read from Asyncify's own data when the unwind
stops. In the measurements of 2026-10-11, the deepest build was one compiled
with optimization and linked without it, as b2's `release` variant links on emscripten:
its deepest suspension in the tests wrote 3,540 bytes, against 1,272 in a
`debug` build. Linked with optimization, a suspension writes a sixth or
less of what it writes linked without: 416 bytes at most in the tests, and 384
for the run family's deepest path, against 2,404. Half of the stack is so
left to the program's own frames, whose depth asio cannot know.

A program that calls `run` deep in its code, or whose frames above `run`
are large, measures its own suspensions the same way and asks for more
with the feature `asyncify-stack-size`, which asio declares: in its
requirements, `<asyncify-stack-size>16384`, or on b2's command line,
`asyncify-stack-size=16384`. Its values are powers of two from 8192, asio's
size and the default, to 1048576; a smaller one stops the program's
compilation at an `#error` of `<webcpp/asio/config.hpp>`, which says why.
asio's usage requirements read the feature, so that its flag ends last on
emcc's command line, where emcc keeps the last: a `<linkflags>` of the
program's own would come before asio's and be ignored.

A suspension that does not fit is found when the unwind stops, after its
frames wrote past Asyncify's stack into the heap; the program aborts there.
Nothing of the program runs afterwards: no destructor or `atexit` handler,
no timer or event of asio's; only JavaScript of the page's own that calls
an export could still enter it.

_Held by_ `asyncify_stack`, with exceptions and without them, in debug,
in release and in release linked with `-O3`, which measures every
suspension of the run family, the reactor's wait and the yield under each
member that makes one, inside a `try` and a `catch` block too, and fails
when one of them leaves less than half of the stack, or when the reading
finds no unwind, no byte written, or no blocking poll in a reactor-wait
case; by every test of the asyncify lane,
which links the same size and traps if a suspension of its own does not
fit; by `asyncify_stack_size_default` and `asyncify_stack_size_raised`,
which read the size the program was linked with, and
`asyncify_stack_size_refused`, which does not compile, beside
`asyncify_stack_size_control`, which does; and by `bridge_abort`, in each
variant, where an event called from JavaScript after the runtime aborted
reaches no registration.

The reactor-wait cases keep outstanding work until a JavaScript macrotask
posts the handler that releases it. Each delays entry by 25 ms, past the
expiry of the former 1 ms {cpp} timer, and requires a poll with a nonzero
timeout. A timer that already expired can finish in the initial
nonblocking poll: that poll suspends too, but its shorter stack is not
evidence for the waiting path. The yield cases cover `run`, `run_for` and
`run_until` separately.

On 2026-10-14, with Emscripten 6.0.11 and Node 26.7.0, the corrected
`asyncify_stack` test measured these maxima from scratch, in bytes:

[cols="2,1,1",options="header"]
|===
| Build | Exceptions on | Exceptions off
| Debug | 1164 | 844
| Release, unoptimized link | 2896 | 1940
| Release, link with `-O3` | 384 | 288
|===

Each of the eleven paths with exceptions and nine without stayed below
4096 bytes, half of the configured 8192. These are measurements of the
run-family test, not a bound on a user's own call frames.

The artifacts are named and placed as Boost's own build names and places
them: one directory level per toolset, variant and property that is not
the default, and a file name that carries the program's tags joined by `-`,
the toolset's version, `60` for Emscripten 6.0.11, `d` for a debug build,
and the suspension variant. The default variant adds no directory level:

[cols="1,4",options="header"]
|===
| Build | The program `app`

| debug, `jspi`
| `+bin/emscripten-6.0.11/debug/.../app-60-d-jspi.js+`

| debug, `asyncify`
| `+bin/emscripten-6.0.11/debug/.../webcpp-suspend-asyncify/app-60-d-asyncify.js+`

| release, `jspi`
| `+bin/emscripten-6.0.11/release/.../app-60-jspi.js+`
|===

each beside its `.wasm`.

[#asio-building-loader]
=== Loading the variant a browser runs

Build a page program and its two variants with `webcpp.variants`:

[listing]
----
include::{library-root}/test/browser/Jamfile[tag=page-variants]
----

The build writes `page_program.variants.json` beside the JSPI artifact.
Its `jspi` and `asyncify` objects each contain a `script` path relative to
the manifest and the WebAssembly size in bytes. Serve the manifest, both
scripts and their WebAssembly files with their relative layout intact.

The loader is `include/webcpp/asio/webcpp-asio-loader.mjs`, shipped with
the headers. A page imports its `load` function and calls
`load('page_program.variants.json')`. It detects JSPI by checking whether
`WebAssembly.Suspending` is a function, chooses `jspi` when it is and
`asyncify` otherwise, and reads the artifact path from the manifest.
It resolves that path relative to the final manifest URL after any HTTP
redirects, imports the script and awaits its default factory. A custom
`fetch` that supplies no response URL uses the requested manifest URL.
The result is `{variant, module}`.

`supportsJspi(scope)` permits detection in a supplied scope. `pick(manifest,
jspi)` returns `{variant, script}` and rejects a missing script for the
selected variant. `load(manifestUrl, options)` accepts an explicit `jspi`
choice, `module` options passed to the factory, and replacements for
`fetch` and `importModule`. Failed manifest requests report their URL and
HTTP status; fetch, JSON, import and initialization failures propagate to
the caller. A failed JSPI load does not silently retry Asyncify.

A relative manifest URL is resolved against the page URL, or against the
loader module URL where no page location exists. Factory completion is
variant-dependent: the current JSPI factory awaits `main`, while Asyncify
can resolve before a suspended `main` finishes. An indefinitely running
JSPI program therefore reports readiness through its module callbacks;
an application observes its own completion signal. The loader test waits for the program's output,
within the driver's timeout, rather than sleeping for an assumed duration.

The `browser` lane loads both variants under Node using a file reader for
the manifest, and in headless Chrome over loopback HTTP. It exercises this
actual page program:

[source]
----
include::{library-root}/test/browser/page_program.cpp[tag=page-program]
----

The same lane checks idle waits and animation callbacks under continuous
ready work in Chrome. See <<asio-testing-browser>> for its measurements
and failure criteria.

[#asio-building-exit-status]
=== The exit status

After a suspension, Asyncify loses the value `main` returns: a program
whose exit status matters, under node, ends with `std::exit`; webcpp's own
tests end through `webcpp::test::exit_status`, and a test that does not
fails
(https://github.com/webcpporg/webcpp/blob/main/AGENTS.md[AGENTS.md]
chapter 9). asio's tests pin both cases where node would read a failure as
a pass, in each variant: a `main` that never finishes, and a `main` that
suspended and then returns 1 without the helper.

[#asio-tls]
=== TLS: build OpenSSL from source on native and WASIp3

For a program including `<webcpp/asio/ssl.hpp>`, add
`/webcpp/asio//openssl` beside `/webcpp/asio//asio` in its target sources:
`exe app : app.cpp /webcpp/asio//asio /webcpp/asio//openssl ;`.
This forwards `/webcpp/third_party//openssl`, which builds OpenSSL 3.5.9
(commit `45e844fa2a14ec92d146bd8f5778ac130b6625fb`) from the unmodified
upstream submodule. No installed OpenSSL or `OPENSSL_ROOT` is used by this target.

In a Git checkout, initialize the source with
`git submodule update --init third_party/libs/openssl`.
A WebCPP source distribution already contains the required OpenSSL files and
does not need Git. The build needs Python 3, Perl, Make, and the selected
compiler toolchain; Git is also used to verify a source checkout.
B2 invokes upstream Configure/Make and exports static `libssl.a`, `libcrypto.a`
and their matching generated headers. Before Configure, it stages the
distributable source files in a temporary directory and verifies their paths,
file modes and content hashes against the pin. Missing, additional or altered
files fail the build. Dot paths and pinned optional upstream repositories are
omitted, just as in the source distribution. The temporary source directory
also avoids upstream Makefiles' restriction on source paths containing spaces.
Different toolsets, optimization flags,
exception settings and thread profiles use separate build directories. Effective
C flags and compiler commands also identify separate archive/header directories.
Flags retain normal B2 scope: dependency-specific `cflags` belong on the OpenSSL
target, not only on its consumer. Independent concurrent B2 processes should use
separate `--build-dir` directories.
`threading=single` builds OpenSSL with `no-threads`; `threading=multi` enables
its platform threading implementation. Native recipes support Clang/GCC on
macOS/Linux and MSVC on Windows. MSVC uses upstream Configure and nmake,
static archives and the B2 runtime/debug settings; the initial Windows recipe
uses portable C without requiring NASM.

For a program built both natively and for the browser, use the condition below.
It also selects OpenSSL for WASIp3; browser builds retain the settings adapter:

[listing]
----
include::{library-root}/example/tls/Jamfile[tag=project,indent=0]
----

Do not use `<toolset>!emscripten:<library>/webcpp/asio//openssl`: that spelling
silently fails to link OpenSSL in the tested B2 configuration.

Correct configuration errors as follows:

* If `ssl.hpp` reports that OpenSSL is not linked, name the `openssl` target.
  Outside B2, define `WEBCPP_ASIO_HAS_OPENSSL=1` and supply matching headers,
  libssl, libcrypto and platform dependencies yourself.
* If the source checkout is missing, initialize the submodule with the command
  above. Tests requiring OpenSSL fail rather than silently skipping TLS.
* If the target is named for the browser or WASIp2, select native or WASIp3.
  The browser settings record does not implement TLS inside the Wasm module.
* With WASIp3 `threading=multi`, use `exception-handling=off` with wasi-sdk 34.0:
  its cooperative sysroot does not contain the {cpp} exception runtime.

The built-in default and base providers are linked statically. Loading provider
modules is disabled; this configuration is not a FIPS build. WASIp3 also disables
assembly, dynamic loading, QUIC, Unix-domain sockets and the OpenSSL thread pool.
Native Clang/GCC builds retain upstream assembly optimizations; the initial
MSVC recipe uses portable C. The recipe uses function and data sections plus
platform dead stripping. A program has one OpenSSL provider. Native Trystero's
`/webcpp/trystero//native` target builds pinned static libdatachannel and its
required nested sources against this same provider, so it can coexist with
Asio and Beast. Such a program selects `threading=multi` and exceptions for
Trystero's worker-thread backend. Libsecp256k1 remains externally provisioned;
`OPENSSL_ROOT` and `LIBDATACHANNEL_ROOT` do not select alternate providers.

The configured certificate directory is `/etc/ssl`. A source-built library does
not install a system trust store or import the macOS keychain. Use the embedded
factory in <<asio-ca-certificates>> for portable defaults, or explicitly load
the intended CA file, set `verify_peer`, and verify the peer's hostname on a raw
context. WASI applications using a file must preopen its directory. Embedded
authorities need no certificate filesystem access. Both require the needed TCP
network capability; linking the library grants no runtime permission.

WASIp3 seeding explicitly selects OpenSSL's `getrandom` configuration, whose
WASI implementation calls `getentropy`, then wasi-libc's secure
`wasi:random/random.get-random-bytes` host import. With Wasmtime's default host
configuration, the generator is seeded from the operating system. The host
remains trusted: an embedder can replace its randomness provider. The tests
verify that host entropy is requested and a reported entropy failure prevents
random output and key generation; they do not prove cryptographic entropy
quality or snapshot/restore safety. Reseed policy after restoring a seeded
instance requires separate validation.

The reproducible local test driver is `python3 tools/openssl/test/run.py --fresh`
from the superproject. It needs Python with TLS 1.3 and an OpenSSL 3 command-line
program only to create short-lived server fixtures. The client links the
source-built library. `WASMTIME` selects the runtime executable; the recorded
WASIp3 checks use wasi-sdk 34.0 and Wasmtime 50.0.1. See
<<asio-capabilities-network>> for the target/variant matrix.

The recurring own lane `b2 libs/asio/test/tls//tls-integration` drives those
TLS, embedded-CA, state, cancellation and entropy fixtures on native and WASIp3
profiles. `b2 libs/asio/test/tls//openssl-upstream` is native only: it requests
`webcpp-openssl-tests=on`, builds and runs upstream's full `alltests` suite,
then links a TLS consumer against those exact archives. The
`openssl-upstream-msvc-14.3` and `openssl-upstream-msvc-14.5` aliases exercise
that suite with the corresponding Windows CI toolsets. Ordinary consumers do
not run that suite. The upstream harness is unavailable on WASIp3; the separate
integration tests give narrower evidence and do not claim upstream-suite parity.
A lane declaration is not evidence that the current candidate passed CI.

[#asio-ca-certificates]
=== How-to: configure trusted certificate authorities

For a native or WASIp3 client with portable trust defaults, include
`<webcpp/asio/tls_client_context.hpp>` and link `/webcpp/asio//tls`.
The target includes Asio, source-built OpenSSL and
`/webcpp/third_party//ca_certificates`. No certificate file, environment setting,
system trust store or network download is read by the factory. WASIp3 needs no
certificate directory preopen; a network connection still needs host permission.

This program prepares the context and checks errors without exceptions. With no
arguments it uses the embedded roots. An optional argument supplies replacement
PEM bytes, not a file path:

[source,cpp]
----
include::{examples}/asio_tls_client.cpp[tag=program,indent=0]
----

The default invocation prints:

[listing]
----
include::{examples}/asio_tls_client.expected[]
----

Use the resulting context when constructing TLS streams and keep it alive while
they exist. The factory enables `verify_peer` and requires TLS 1.2 or newer.
Configure `ssl::host_name_verification` for the expected hostname and set SNI on
each connection. A trusted issuer alone does not establish the intended hostname.

The overload taking `std::string_view` replaces the complete trust set. It does
not append private authorities to public roots. Supply one or more PEM CA
certificates separated by whitespace. Empty input, malformed certificates,
non-CA certificates, and trailing non-whitespace data return an error without
a usable context. The certificates are copied into the context; the input may
then be released. Initialization failures are errors as values too, with or
without exceptions. OpenSSL owns its allocations and does not use an Asio
allocator. On Emscripten the helper returns `unsupported_target`: browser TLS
and its trust policy remain under the browser's control.

==== Updating the embedded snapshot

The source is the https://curl.se/docs/caextract.html[Mozilla CA export from curl],
preserved in `third_party/ca_certificates/cacert.pem` with its MPL-2.0 license.
The adjacent manifest records the source URL, date, SHA-256 and each certificate's
DER fingerprint. The initial snapshot is dated 2026-09-25 and contains 121 CAs.
Keep its license and corresponding PEM source available when redistributing it.

Choose a published date from the curl CA Extract page. From the superproject root:

[source,bash]
----
python3 tools/ca_certificates/update.py --date 2026-09-25
python3 tools/test/ca_certificates_test.py
python3 tools/test/ca_certificates_b2_test.py
python3 tools/ca_certificates/run.py --fresh
----

The updater downloads through verified HTTPS, checks the published SHA-256,
validates every certificate and reports added/removed fingerprints. Review the
trust changes and version the PEM and manifest together. An older date is
rejected. Use `--output DIRECTORY` to stage a candidate separately, or
`--source-file PATH --sha256 DIGEST` for an independently authenticated offline
copy. A checksum detects a changed artifact; it is not an independent publisher
signature. Normal builds use the pinned artifact without downloading anything.

Rebuild and redeploy applications after changing the snapshot. Existing binaries
retain their embedded roots. The updater does not schedule downloads or alter
running programs. The build rejects a missing or hash-mismatched snapshot. If an
update was interrupted between replacing its two files, restore both from Git
and repeat it. Run only one updater per output directory.

==== Using installed headers

`b2 install --prefix=DIR` includes the generated
`webcpp/asio/detail/ca_certificates.hpp` under `DIR/include/`. Its private
namespace is `webcpp::asio::detail::ca_certificates`. The matching PEM
source, manifest and MPL notices are under `DIR/include/webcpp/ca_certificates/`.
The CA package is generated locally without compiling OpenSSL. A consumer of
the installed TLS header must still configure Boost, define
`WEBCPP_ASIO_HAS_OPENSSL=1` and link compatible OpenSSL headers and archives.
Installation does not package the Cobalt runner or dependency archives.

==== What portable trust does and does not mean

The PEM export omits some additional constraints enforced by Firefox. It does
not reproduce the complete browser policy, consult the host's private roots or
automatically fetch revocation information. Explicit replacement lets an
application choose a narrower or organizational trust set. Native system trust
integration and automatic runtime updates are separate features.

Local tests cover real TLS 1.2/1.3 connections, wrong hostnames, an unrelated CA,
and rejection of a private test CA by the default public bundle. They also check
complete replacement and invalid input. The matrix covers native macOS
single/multi with exceptions on/off, WASIp3 single with exceptions on/off, and
WASIp3 cooperative threads with exceptions off under SDK 34. The WASIp3 client
runs without certificate filesystem grants. Tests use a fresh local test CA;
they do not depend on a public website's availability.
