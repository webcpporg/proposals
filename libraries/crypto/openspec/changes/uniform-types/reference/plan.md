# Uniform types Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every signature and every X25519 key of webcpp::crypto has a type of its own; Ethereum's recoverable ECDSA and Ed25519ph (`eddsa_prehashed`) are schemes; key pairs, AEADs and boxes are checked by concepts; constructions are grouped by purpose; every fallible factory is named by its input; plus three small fixes (a throwing `getRandomValues` in the browser, a public `crypto::erase_secret` with `crypto::equal` renamed `crypto::constant_time_equal`, no one-word local in a header); the AEAD contract in `crypto::secret_key_encryption::aead` with secretbox beside it in `crypto::secret_key_encryption`, and every public name spelled out (owner decision 13).

**Architecture:** One class template `detail::basic_signature<Tag, Size>` (new `detail/signature.hpp`) gives the five signature types by tag (Ed25519ph's scheme `eddsa_prehashed` gives `ed25519::signature`, owner decision 12); the trait `detail::signature_of<Key, Scheme>` pairs a key with its signature type, and every `verify` overload takes `Signature const&` and checks it with a `static_assert` that names the type expected. `curves/x25519.hpp` gains `public_key` and `basic_keypair<B>`; `key_exchange/kx.hpp`, `public_key_encryption/box.hpp` and `sealed_box.hpp` (moved from `curves/x25519/` and `hybrid/`) take them. `keypair.hpp` splits the contract into `keypair`, `signing_keypair`, `agreement_keypair`; `secret_key_encryption/aead.hpp` holds the AEAD contract, `secret_key_encryption::aead::cipher`, `streaming_cipher` and the free `seal`/`open` (3.2 creates it and moves the free forms there, 3.3 the asynchronous ones), and `secret_key_encryption/authenticated_box.hpp` the box concept `secret_key_encryption::authenticated_box` and the box forms; `factories.hpp` (was `make.hpp`) holds `from_secret`, `from_bytes`, `from_key`, `generate`. `async.hpp` defines every asynchronous member, as on crypto/sign-unified. Every caller of a removed name moves in the task that removes it (design D7), so libs/crypto builds and its tests pass at the end of every task.

    { Keypair::generate() } -> std::same_as<boost::system::result<Keypair>>;
    { std::declval<Keypair const&>().public_key() } -> std::same_as<boost::system::result<typename Keypair::public_key_type>>;
    { std::declval<Keypair const&>().secret() } -> std::same_as<boost::system::result<secret<Keypair::secret_key_size>>>;
};
namespace detail {
// signs_as_declared<K, S> also requires the result to be result<signature_of_t<K, S>>
template <class Keypair, class List>
concept signing_keypair_over = keypair<Keypair> && signs_some_scheme_v<Keypair, List> && signs_every_declared_v<Keypair, List>;
template <class Type> inline constexpr bool is_secret_result_v = false;  // true for result<secret<N>>
}

## Rulings made in the plan

- **P1, the order** (header): X3, 2.5 and 2.4 first. Cost if wrong: none in behaviour; a late 2.5 would rename the new types' `make` twice.
- **P2, X3's test is new.** The brief's "existing MSVC hides-no-user-name test" (48ca7ef) does not exist: that commit renamed `make.hpp`'s parameters; a200e69 moved a test's global into a local. `user_globals_test.cpp` declares the survey's names before every public header, its third-party headers included first; only MSVC diagnoses (clang and GCC `-Wshadow` never warn across namespaces, checked). Cost: a one-word name added later outside the list is caught only when it collides on MSVC.
- **P3, X3's names**: the table in X3, "role then kind"; `timing_scope` for the guard. Cost: a rename of renames if the owner prefers another word.
- **P4, engine statics named `make` are renamed** (`import_secret`, `seed_keypair`, `heavy_state::allocate`): the spec says no function is named `make`; decision 9's "backends' internal capabilities keep their names" means the capability rows (`*_import`), which stay. Cost: internal only.
- **P5 (superseded by owner decision 12, 2026-11-23): no distinct Ed25519ph signature type.** The first ruling was `curves::ed25519::ph_signature`; Ed25519ph is now the scheme `eddsa_prehashed` (Task 1.4, design D9), whose signature is `ed25519::signature`, so 1.1 creates no `ph_signature` and 1.2 retypes the streaming signer onto `ed25519::signature`. Cost: an Ed25519ph signature given to the pure `verify` fails at run time with `invalid_signature` instead of stopping the build (RFC 8032's domain separation makes it fail; the page says the two are not interchangeable).
- **P6, signatures have a public default constructor (all zeros)**, so they are `std::regular` as the spec says and the asynchronous error completion's empty value exists. Cost: a zero signature can be named; every verify refuses it.
- **P7, `can_verify` gains the signature: `can_verify<Scheme, Signature, Input, PublicKey>`** (D1 says it is false for a signature of another curve), with `detail::signature_of<Key, Scheme>` as "the trait gains the signature type" (a scheme alone does not know its curve). Cost: callers of the concept add one argument.
- **P8, `to_der`, `from_der`, `normalize_low_s`, `is_low_s` take and give the typed ECDSA signature** on both curves (D1 names the last two; the first two would otherwise be the last byte-signature functions). Cost: the formats change builds on typed values, as it intends.
- **P9, MuSig2's aggregate is a `schnorr_signature`**; partial signatures keep their bytes (crypto-sign's R7). Cost: MuSig2 callers add `.bytes()`.
- **P10, secretbox gets its own engine** (`detail::secretbox_state`/`secretbox_engine`, no associated-data parameter) and its families move to `secret_key_encryption/secretbox.hpp` (X4 moved the header), so that `ciphers::aead` names only AEADs. Cost: sodium.hpp's two specializations rewritten.
- **P11, no `async_from_keys` for crypto_box**: D6 lists `async_from_key` alone; a box is made from typed keys. Cost: a program that wants it posts the synchronous call itself.
- **P12, D6's refusal fires before any member of the type is named**, and its text lists the algorithms (a C++20 `static_assert` cannot compose the type's name). Cost: the message does not name the one type used.
- **P13, `detail::x25519_access`** gives kx, the boxes and the sealed box the key pair's bytes without a nested guard or a copy. Cost: one friend struct.
- **P14, `kx_keypair::from_keypair` takes the key pair by value** (a sink; the key pair is move-only), and `keypair()` gives it back by reference. Cost: an lvalue needs `std::move`.
- **P15, X1 calls `crypto.getRandomValues` from its own `EM_JS`** through a fresh `Uint8Array`: no `crypto` object is `not_supported` (the audio worklet's case, kept), a throw is `entropy_unavailable`. Cost: node versions without `globalThis.crypto` (before 19, which webcpp does not run) would read `not_supported`.
- **P16, `crypto::erase_secret` (owner decision 11; `crypto::wipe` in the first draft) is one constrained template plus a refusing overload**; no `(void*, size)` form (no caller needs it). Cost: a C buffer of runtime size goes through `std::span`.
- **P17, the free X25519 byte `async_agree` is removed in 2.1** and `async_agree` becomes one template constrained by `agreement_keypair` in 3.1.
- **P18, `doc/hybrid.adoc` becomes `doc/public_key_encryption.adoc`** with its anchor; `kx.adoc` keeps its name.
- **P19, the free factories hold a guard**, as `crypto::make` did, even over a member that calls no backend (`from_bytes` of a signature). Cost: DIT set around a copy.
- **P20, `to_x25519()` gives a key pair of the same backend**, refused at compile time when that backend has no X25519.
- **P21, 1.1's message tests for a signature of another curve move to 1.2**, where `verify` first takes the types.

- **P22, the Keccak message form needs `/third_party//xkcp` in the program's Jamfile** (R19): secp256k1's family default does not bring XKCP, which builds on every target and toolset; a marker needs none. Cost: an Ethereum program adds one Jamfile line.
- **P23, both recoverable schemes share `recoverable_signature`** (the controller's ruling, R20). Cost: a signature recovered under the wrong scheme gives a wrong key at run time, not a build error.
- **P24, `ecdsa_keccak256_recoverable` has no `verify`**: `ecdsa_sha256_recoverable` has none (the catch-all sends its signature to `recover`), so symmetry says none (R18).
- **P25, X1b installs crypto's implementation unconditionally on Emscripten**, before crypto's first `sodium_init`: libsodium has no way to read the current implementation without initialising it, which runs the stir that throws. Cost: a program's own implementation set earlier is replaced (the page says to set it later).
- **P26, a failed draw outside a call crypto observes calls `sodium_misuse()`**, libsodium's abort: handing zeros to a caller that cannot see a failure would be worse. Cost: the program's own libsodium calls still stop on a failed generator, as libsodium intends.
- **P27, `sign(eddsa_prehashed, ...)` and its `verify` call libsodium's `_crypto_sign_ed25519_detached` and `_crypto_sign_ed25519_verify_detached` with `prehashed` 1**, declared `extern "C"` in `backends/sodium.hpp` as libsodium's private `crypto_sign/ed25519/ref10/sign_ed25519_ref10.h` declares them: libsodium's public API signs Ed25519ph only from its own SHA-512 state (`crypto_sign_ed25519ph_final_create`), which cannot be given a finished digest, and these are the functions that state's `final_create` and `final_verify` call, so strictness and the signature are libsodium's. They link because webcpp builds libsodium from source as a static library on every target. Cost: an internal symbol a libsodium upgrade could rename (the vendored version is pinned; `ed25519ph_sodium`'s `streaming_equals_scheme` catches a mismatch); the alternative, Ed25519ph rebuilt over libsodium's public scalar and point operations, would be a new secret path of crypto's own.
- **P28, X2 lands before 1.1** with both parts of owner decision 11, so that the new tests of 1.1 to 3.3 call `constant_time_equal` from the start; `equal` and `ph` each get a removal message test (`equal_removed`, `equal_header_removed`, `ph_removed`), as `make_removed` does. Cost: X2 touches libs/hash and 17 fixtures early, in a task the first draft called small.
- **P30, X4 runs right after 2.1, and 3.2 and 3.3 do the moves** (the controller's ruling on owner decision 13, R23, recorded when 2.1 was built): "3.2 and 3.3 are written with decision 13's names; X4 covers the renames they do not touch". X4 renames in place (parameters, `nonce_size`, `max_nonce_size`, `max_associated_data_size`, `invalid_nonce_size`, `auxiliary_random_bytes`, the guideline), so the names 3.2 and 3.3 move already carry the renames and their new signatures use `nonce`, `nonce_size` and `associated_data` from the start. X4 is two commits (parameters; other public names) so that review can take them apart. Cost: X4 touches 53 files of libs/crypto and 4 of the superproject before 2.2; 3.2 grows by the moves of the free forms and secretbox (17 tests, 2 examples, the pages, 3 fixtures).
- **P31, the box forms follow `authenticated_box` into `secret_key_encryption`** (design R21, the coordinator's refinement): `secret_key_encryption::authenticated_box` in `secret_key_encryption/authenticated_box.hpp`, beside the secret box, and `secret_key_encryption::seal`/`open` (3.3: `async_seal`/`async_open`) for a secret box and a crypto_box alike; none in `crypto::` nor in `public_key_encryption`. Cost: a crypto_box's free form is named through `secret_key_encryption`, not found by argument-dependent lookup.
- **P32, decision 13 covers the public names around the parameters** (design R22, accepted by the coordinator): `iv_size`, `max_iv_size`, `max_additional_data_size` and `error::invalid_iv_size` become `nonce_size`, `max_nonce_size`, `max_associated_data_size` and `invalid_nonce_size` (value 2 kept), in X4; `max_` stays (the standard library's word); BIP340's `aux_random` becomes `auxiliary_random_bytes`. Cost: an error enumerator renamed (69 uses).

- **P29, the message tests and the fixture named `ed25519ph_*` keep their directory names** (Ed25519ph is the algorithm's name; the capability row `ed25519ph` keeps its name, R17); only their code and texts change. Cost: none.
